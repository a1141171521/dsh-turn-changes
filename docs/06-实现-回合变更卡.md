# 实施记录：回合变更汇总卡（chgset-1）

> 路线 A 的落地。对应调研见同目录 `00-总览.md` 第四节。
> 插件形态：**动态 Cordis Plugin**（进程内临时扩展，不写仓库源码、不落盘、重启即消失）。
>
> **当前状态：`pkg-7`。第一至四节记录的是 pkg-5 及更早的实现，其中若干结论已被第九节推翻——请先读第九节。**

## 一、决策依据

调研得出的三条落差决定了整个设计：

| 事实 | 对设计的影响 |
|---|---|
| `edit`/`write` 的就地 diff **DSH 已内置**（`file-mutation-toolview` → `FileMutationRow` → `DiffBlock`） | 不重做逐次 diff，只补**回合级汇总** |
| DSH 没有回合级变更聚合（全仓 grep `changeSet`/`turnChanges` 零命中） | 这是要补的空白 |
| `conversation.chat.turnTail` 已被 `ui-deliverables` 占用 | 必须处理座位冲突 |

用户裁决：**接受遮蔽、但保留原功能**；不涉及移动端。

## 二、与 Cindy 的对应关系

| Cindy | 本插件 | 说明 |
|---|---|---|
| `TurnChangesCard` 默认显示前 3 个文件行 | `VISIBLE_FILES = 5` | pkg-7 起先列 5 个，其余折叠成「再显示 N 个文件」 |
| 零文件不入列表（`hasReviewableTurnChanges`） | 选择器直接不接手 | 等价效果，且更省 |
| 零文件**刻意不显示 `+0 −0`** | 增删为 0 时该 span 不渲染 | 照搬理由：会被误读成「没有变化」 |
| 整轮 undo / reapply | **未做** | `撤销` 按钮当前为禁用态，理由见 9.5 |
| 快照前像（copy-on-write）+ `turn_diff` 事件 | **用工具结果自带的整份文件前后文** | `edit`/`write` 的 `value` 自带整份文件，见 9.2 |
| `incompleteReasons[]` + `isReversible` | `truncated` 布尔 + `untracked` 警告横幅 | 见 9.5 与边界 12 |

## 三、实现要点

### Host 半部

**采集：不抓前像，直接读工具结果。** Cindy 需要在 `PreToolUse` 时把文件内容读进内存，
是因为它的 agent 侧不保证给 diff。DSH 不同——`edit`/`write` 的工具结果 `meta.diffs`
与官方 `DiffBlock` 渲染用的是同一份数据。所以本插件在 `tools/result` 上**只读**这份结果，
不碰磁盘，也不注册 `fs/edit-intent` 之类的钩子。

**计数（`pkg-5` 的做法）：照抄平台语义，不自建 diff 引擎。** —— 该取舍已被 9.1 推翻，此处保留为历史。

`meta.diffs` 里的 `oldText` / `newText` **既不是整份文件、也不是模型传入的原文片段**，
而是 `structuredPatch("", "", before, after, void 0, void 0, { context: 3 })` 产出的
**带 3 行上下文的 hunk 文本**（`dsh-tool-fs/lib/index.js:484-507`）：

- 上下文行**同时**进入 `oldText` 和 `newText`；
- `-` 行只进 `oldText`，`+` 行只进 `newText`，`\ No newline` 标记被跳过；
- 纯插入时 `oldText` 为 `null`；
- 散落的改动是**多个独立 hunk**，且**共享同一个 `path`**。

官方内联卡的计数就是这两个文本的行数——`contentLines(newText)` 与
`contentLines(oldText)` 逐 hunk 相加（`dsh-client-ui-primitives/lib/index.js:4769`、`4826`），
**不做任何 LCS**。

`pkg-5` 因此也这么做：hunk 文本按行计数、同一路径的多个 hunk 求和，
理由是**与上方那张内联 diff 卡逐项相等**。

**这一段在 `pkg-6` 被推翻**：照搬 Cindy 之后，计数改为纯改动行，
行级 diff 改由自建引擎产出（见 9.1 / 9.3）。代价是同一屏里出现两个口径的数字。

**回合边界：用会话日志，不用 agent 事件。** `session/event` 的 `turn/end` 带
`event.data.turn`，这个号与客户端 `turnTail` 收到的 `turn.turn` 是同一个数——
所以两边无需额外协商就能对上号。这也是选择它而非 `agent/turn-stopping` 的原因
（后者不提供可与客户端对齐的编号）。

**对模型的暴露面：零。** 不注册任何 Tool、不注入系统提示词——插件只做 UI，不改变 agent 行为。

### Client 半部

**抢座**：`conversation.chat.turnTail`，`priority: -1`。该槽是 chain，
排序只看 `priority`（`dsh-client-ui-slots/lib/index.js:130`），同优先级才按注册顺序；
`ui-deliverables` 用默认 0，所以 -1 稳定排到它前面。

**选择器必须是同步纯函数**（chain 槽的 `select` 不能异步），所以索引维护在组件之外：
长轮询 Host 的 `turn-changes/poll`，拿到新条目后**重新注册一次**槽位条目来触发链重算。

**只传纯 JSON**：Host 侧所有返回值都是自己构造的字面量对象，从不序列化任何 live 对象。

**视觉**（`pkg-4`）：只用主题 token，12px 圆角，字号跟随用户设置。

这里踩的坑值得单独记下来。第一版按「常规做法」写——`bg-layer-1` 作填充、`1px border-l1` 作边框——
结果用户的原话是「**边框不太明显，让人感觉不到这是一个卡片**」。去读主题真值才发现原因：

> **浅色主题下 `--dsw-alias-bg-base`、`--dsw-alias-bg-layer-1`、`--dsw-alias-bg-layer-2`
> 全都是 `#fff`**，三者**没有任何色差**；而 `--dsw-alias-border-l1` 是 `#0000000a`，只有 4% 黑。
> 也就是说，卡片的填充色与页面背景**完全同色**，边框则是几乎看不见的一层灰。

（这些值不在 Inspect 的 `Theme.listTokens` 返回里——那份列表只覆盖可被插件覆盖的别名子集，
真值要从 `dsh-client-ui-theme/lib/client.js:1053` 的静态 token 表里读。）

平台上真正有对比度的表面只有三个：

| token | 浅色值 | 深色值 | 用途 |
|---|---|---|---|
| `--dsw-alias-border-l2` | `#0000001a`（10% 黑，l1 的 2.5 倍） | `#ffffff1f` | 卡片外框、表头分隔线 |
| `--dsw-alias-markdown-code-block` | `#f9fafb` | `neutral-bluish-900` | 凹陷表面（官方 bash 卡片就用它填充） |
| `--dsw-alias-interactive-bg-hover` | `#2631480f` | `#ffffff14` | 交互悬停底色 |

最终做法：`markdown-code-block` 填充 + `1px border-l2` 外框
+ 表头用 `bg-layer-1` 形成双色带 + 一道 `border-l2` 分隔线
+ 极轻投影 `0 1px 2px rgba(0,0,0,.04)`（浅色下补足层次，深色下几乎不可见）。
行内分隔线用更弱的 `border-l1`，让「卡片外框 / 表头分隔 / 行间分隔」形成明确层次。

其余取舍：

- **两行式文件行**：第一行文件名（`label-primary`），第二行目录（`label-caption`），
  超过两段目录折叠成 `…/reports/cindy`。长绝对路径不再被一行截断到看不出是哪个文件。
- **表头始终存在**：它给卡片身份，也让边框围住的不再是一片空白。
  单文件时表头不重复总数（行内数字已经完整，重复一次就是噪音）。
- **去掉常显下划线**：只在悬停时出现，同时整行底色变 `interactive-bg-hover`。
  常显下划线会让每一行都像链接。
- **字号跟随用户设置**：统一用 `--dsh-content-font-size-secondary` 与
  `--dsh-content-font-delta`，等宽用 `--ds-font-family-code`。
  此前硬编码 px，用户在设置里改字号时这张卡不会跟着变——而平台自己的卡片全都跟随。
- 增删用 `state-success-primary` / `state-error-primary`，等宽 + `tabular-nums`。
- 新增文件（仅当 `write` 结果无 hunk 时可判定）在文件名前加绿点。

**点击文件名会发生什么**（用户实测问过这个问题，故记录明确）：卡片调用的是槽位宿主传入的
`openFile`——**与官方 `ui-deliverables` 产物行是同一个函数**，所以点我的行与点官方产物行
行为完全一致。这正是「接受遮蔽、保留原功能」的落点。完整链路：

1. `openFile(path)`（`dsh-client-ui-chat:8124`）先用 `resolveWorkspacePath(cwd, path)` 处理路径。
   该函数对**绝对路径与 Windows 风格路径原样返回**（`ui-chat:27-31`），
   所以本卡片传的绝对 `displayPath` 不会被错误拼接。
2. 转为远端调用 `session.openWorkspacePath`（`dsh-api-session-controller:2799`）。
3. 宿主执行 `this.openPath`，默认实现是 **`openNativePath`**——即交给**操作系统的默认打开方式**。
   宿主侧另有 `config.nativeOpen` / `canOpenNativePath()` 作为能力开关。

因此「点 `.md` 会用 Trae 打开」**不是插件的选择**，而是这台机器上 `.md` 的系统默认关联。
希望它在别的程序里打开，要改的是系统文件关联，不是插件配置。

（补充：官方产物行只在「在文件夹中显示」按钮上用了 `canOpenPath` 门禁，
文件本身始终可点。本卡片不做那个按钮，因此可点行为与官方一致，未引入假的 affordance。）

## 四、右侧栏 diff 面板（pkg-5）

### 为什么不能走"选中 tool call 再由官方面板渲染"

最初设想是让点击去选中对应 tool call、复用官方 DetailsPanel 的 diff 渲染。查证后否掉：

- `ui-tool:1339` 的 `inspect` 实际是 `inspectCall(callId)` → `ui-chat:2020` →
  `openView("trajectory", callId)`，即**把对话切到轨迹视图**，并不是打开右栏。
- 右栏内容由 chat store 的 `selection.callId` 驱动（`ui-chat:2018`、`ui-chat:7023`），
  而客户端服务清单（layout / locale / sessions / slots / theme / timer / uiWorkspace / workspaces）
  里**没有会话选择服务**——动态插件够不到那个 store。

### 结论：右栏是一块闲置的官方区域

- 右栏是 `details` 槽（`single`、session 作用域），由 `ui-layout:259` 的 `renderSlot("details")` 渲染，
  宽度 300–520 可拖（`ui-layout:35-52`），`openDetails()` 把宽度设为 360。
- **在整个 `resources/app` 内 grep `openDetails`：只有定义与 layout 服务自身，没有任何调用者。**
  也就是说这块官方区域在当前 UI 里没有入口。
- 因此占用它是**占用闲置区域**，而不是夺走在用功能。实测占位结果见第六节。
  **更正**：这里原本写的是「`priority: -1`；单例槽按 `priority` 升序排序、首个生效」，
  该说法已被 9.8 推翻——非 chain 槽传入的 `priority` 会被运行时丢弃。

### 渲染与数字同源：转写权威函数，不自研引擎

| 来源 | 转写内容 |
|---|---|
| `ui-primitives:4787-4816` `buildRows` | 行构造：`oldText` 全部行 → `del`，`newText` 全部行 → `add`，同文件后续 hunk 前插一个 `⋯` 间隔行 |
| `ui-primitives:4765-4776` `diffTotals` | 计数：与卡片同一套 `contentLines` 约定 |
| `DiffBlock.module.css` | 配色：`del` = `state-error-primary`、`add` = `state-success-primary`、`gap` = `label-tertiary`、`path` = `label-primary/600`；**平台不给增删行加背景色块**，本面板同样只着色文字 |

于是**右栏渲染出的行、卡片里的 `+N −M`、平台内联卡的数字，三者同源**，不会互相打架。
（唯一有意的偏离：单文件面板省略 `buildRows` 的路径头行，因为面板头部已经写明文件名。）

### 数据通路

`turn-changes/file` 按需取单文件 hunk，**不进长轮询负载**（否则每次变更都要搬运全文）。
Host 侧计数始终完整（增量累加），只有留存的行数触顶（`MAX_STORED_HUNK_LINES = 4000`）时
才停止留存，并由 `truncated` 如实上报，面板脚注写明「计数为完整值」。

### 点击语义的变化与保留

- 行主体点击 → 在右栏看该文件本轮 diff。
- 行尾 hover 出现的 `↗` → 仍是原来的 `openFile`（系统默认程序打开），**旧能力未丢**。
- 拿不到 `layout` 服务时，行点击自动回退到 `openFile`，不会出现「点了没反应」。

## 五、修正记录

### pkg-2：去掉对 `turn/start` 的依赖

首版（`pkg-1`）在 `tools/result` 里用「当前打开的回合号」归属改动，而那个号来自 `turn/start`。
缺陷是：插件可能在某个回合**进行到一半时**才被激活——开发过程中正是这种情况，
那一轮的 `turn/start` 在插件运行之前就写进了会话日志，于是 `openTurn` 为空，
本轮所有改动被**静默丢弃**（不报错，只是卡片不出现——最难查的那类）。

正确做法是**不依赖任何「开始」事件**：采集侧只按会话累积文件，
回合号在 `turn/end` 那一刻从事件里取。`turn/end` 必然会被观察到，因为只有它代表回合真的结束了。

### pkg-3：修正计数语义与同路径聚合

首版还有两个叠在一起的 bug，症状是卡片显示 `+6 −5`，而正确答案应该是别的数：

1. **语义错**：自建了一套「剥公共前后缀 + 滚动数组 LCS」的引擎，跑在**已经 diff 过的 hunk 文本**上。
   结果是把上下文行当成了冗余、还把 hunk 文本当成了整份文件——数字永远对不上官方内联卡。
2. **聚合错**：同一次 `edit` 的散落改动会产出**多个同路径 hunk**，
   而首版把「同路径再次出现」误解为「文件被再次写入」，用后一个 `after` **覆盖**了前一个，
   直接丢掉了其余 hunk。

`pkg-3` 把这两件事一起改掉：删掉整个 LCS 引擎（连它的测试脚本一并删除），
改为 hunk 文本按行计数、同路径求和。实现因此短了一大截，而且不再有任何
「自己发明一套 diff 语义」的风险。

## 七、已知边界（未做 / 未验证）

1. **没有整轮撤销**。Cindy 的回滚依赖独立的 git shadow savepoint 系统（临时 index +
   `commit-tree` + `update-ref` CAS，挂 `refs/cindy/savepoints/<sid>`），与本卡片的
   change set 是**两套互不相干的数据**。移植它等于再建一套快照系统，超出本次范围。
2. **`bash` 等工具的间接改动看不到**。只覆盖 `edit`/`write` 的结果上报。
   Cindy 也承认这一点（它只是额外用 git 兜底）。
3. **子 agent 的改动按子会话记账**。`exec.agent.id` 是子会话时，条目会落在子会话名下；
   父会话的卡片不含这些文件。是否要合并到父回合，需要产品决策。
4. **计数包含上下文行**。这是**刻意**跟随平台语义的结果：一次单行修改会显示成 `+4 −4`
   （3 行上下文 + 1 行改动），看起来比直觉偏大。改成「只数改动行」会更符合直觉，
   但会与上方内联卡的数字不一致——在两难里选了一致性。
5. **平台固有的一处少算**。当某个 hunk 的某一侧文本恰好是空字符串时，`contentLines('')`
   返回 0 行，而在 diff 语义里那应当是一行空行。最典型的触发场景是
   「把文件唯一的一行清空」：平台给出 `+0 −1`，而行数其实没有变化。
   插件**刻意继承**这个行为——修掉它反而会与内联卡不一致。
   回归脚本把它记为 `named:唯一一行被清空`，是唯一不满足编辑脚本不变量的用例。
6. **`write` 覆盖（内容完全相同）会被误判为新增**。判定新增用的是「`write` 结果里没有 hunk」，
   而内容完全相同时官方也走同一条回退路径，所以这里与官方行为一致，但两者同样不精确。
7. **回合中途激活之前的改动收不到**。事件驱动采集的固有下限，不是调参能解决的。
8. **轮询失败时静默重试**，没有面向用户的错误提示——沿用「不给假 affordance」的取向，
   失败的表现是卡片不出现（与没有这个插件时的行为一致），而不是弹一个点不动的错误。
9. **右栏是官方槽位，注册即接管**。`details` 是 `single` 槽，原本属于 `ui-conversation` 的
   DetailsPanel。当前全仓没有任何 `openDetails` 调用者，所以接管不损失可用功能；
   但若将来的版本开始使用这块区域，本插件会挡住它。回滚只需切回 `pkg-4`，一步可退。
10. **面板只渲染单个文件**。右栏基于「点选一个文件」的模型，没有 Cindy 那种多文件
    review 列表与文件树；要看别的文件需回到卡片点另一行。
11. **面板的折叠阈值固定为 16 行**，与平台 `DiffBlock` 的默认 `maxLines` 一致；
    超过则首尾各 8 行加「展开其余 N 行」，不是全部铺开。

## 八、如何停用

- 永久移除：`cordis_undefine chgset-1`（连同全部 Package 一起删除）。

### 9.1 裁决转向：从「与平台一致」改为「照搬 Cindy」

用户看过 Cindy 截图后要求「完全照搬 cindy 的整个方案以及实现方式」。
这推翻了此前「卡片数字必须与平台内联卡逐项相等」的核心取舍，四处直接反转：

| 旧做法（pkg-5） | 新做法（pkg-6 / pkg-7） |
|---|---|
| 计数照抄平台 hunk 语义（含 3 行上下文） | 计数改为**纯改动行**（Cindy / git 口径） |
| 面板只渲染被点选的那一个文件 | 面板列出**本条消息的全部文件** |
| 行 = 平台 hunk 文本（`oldText` 全部行 + `newText` 全部行） | 行 = **自建行级 diff**（真实 unified diff、双列行号） |
| 不抓前像，只读 `meta.diffs` | 从 `result.value` 读**整份文件前后文本** |

因此第三节「计数：照抄平台语义，不自建 diff 引擎」与第四节「渲染与数字同源：转写权威函数」
**均已作废**，第六节中依赖它们的证据行也随之作废。

**这项照搬有一个用户可感知的代价**：现在同一屏里会有两个口径的数字。
一次单行修改，上方官方内联卡显示 `+4 −4`（3 行上下文 + 1 行改动），
本卡片显示 `+1 −0`。这是照搬 Cindy 的必然结果（Cindy 自己就是改行口径），
但它是**对用户早先那个决定的推翻**——想退回平台口径，切回 `pkg-5` 即可。

### 9.2 新的数据来源：工具结果自带整份文件

`dsh-tool-fs` 的 `edit` / `write` 工具结果 `value` 里带整份文件：

- `edit` → `{ path, before, after }`（`dsh-fs-local:801-818` 的 `editText` 返回 `original.content` 与 `edited.content`）
- `write` → `{ path, operation, before, after }`，**新建时 `before` 为 `null`**

Host 半部因此按「每回合每文件：**第一次**捕获的 `before` + **最后一次**捕获的 `after`」配对，
在 `turn/end` 时算出真正的行级 diff。这也顺带修掉了旧版「`write` 内容相同被误判为新增」。

`meta.diffs` 的 hunk 路径**保留为防御性回退**：一旦拿不到整份文件，
仍按平台口径记录计数并把该文件标为 `noRows`，面板显示「该文件没有行级 diff（仅有计数）」——
绝不静默丢掉一个改动过的文件。

### 9.3 自建引擎的可信度

引擎是「裁公共前后缀 → 中段 LCS（`Int32Array` 表，上限 600×600）→ 超限整段替换」。
中段超限时退化为整段替换（中间做成 del+add），与 git 面对整文件重写时的表现一致，
且**任何路径都满足编辑脚本不变量** `增 − 删 ≡ 行数差`。

`reports/cindy/verify-line-diff.mjs` 用平台自带的 `diff@9.0.0` 对拍。
最强的一条断言是**从 ops 反推旧/新文本必须逐字等于原文**——
这一个断言同时证明了增删归属、顺序与行号推进：

| 断言 | 结果 |
|---|---|
| 结构重建（ops → 前后文本逐字相等） | 4012 例全等 |
| 编辑脚本不变量 `增−删 ≡ 行数差` | 4012 例成立 |
| 折叠守恒 `Σ gap.hidden + 可见行 ≡ ops 行数` | 成立 |
| 行号自洽（ops 上最大旧/新行号 ≡ 两侧行数） | 成立 |
| **最小脚本规模** 与 `diffLines` | 4011 例**逐例相等** |
| 锚点：100 行文件末尾追加 1 行 | `+1 −0`，与 Cindy 截图里 `README.md` 同形 ✔ |

**1 处刻意偏离**：文件末尾换行状态改变时（`'a\nb\nc'` → `'a\nb\nc\nd'`），
本引擎 `+1 −0`，而 `diffLines` / git 是 `+2 −1`（git 会打 `\ No newline at end of file`）。
净变化相同，差异只在末行归属——本引擎沿用 **DSH 平台的行模型**（末尾换行是终止符）。
脚本把**两侧行为都钉成断言**，将来 diff 库若改变行为会立即报警。

复跑：`node reports/cindy/verify-line-diff.mjs`

### 9.4 pkg-6 的致命 bug（pkg-7 修复）

`pkg-6` 的条目创建语句是 `{ path, before: null, after: '', seen: true, ... }`，
而首次捕获的判断是 `if (entry.seen !== true) { entry.seen = true; entry.before = before }`
——**创建时就已经是 `true`**，所以 `entry.before` 永远不被赋值。

后果：每个被修改的文件都被判成「新建」，diff 变成整份文件新增
（`+150 −0` 而不是 `+5 −3`）。**引擎验证全过、接线全错**，这是 pkg-6 的真实状态。
pkg-7 改用 `fresh` 标记：创建时 `fresh: true`，首次捕获写入 `before` 后置 `false`。

同版还修了两处：

- 文件名上的 `direction: rtl`（为做「保留路径尾部」的省略号技巧）会把
  `.gitignore` 这类以中性字符开头/结尾的名字按 bidi 重排，已去掉。
- 卡片丢失的文件数上限已恢复：先列 5 个，其余折叠成「再显示 N 个文件」。

### 9.8 一处修正：单例槽的 `priority` 由运行时分配，我传的值被丢弃

`Slots.listSubTree('details')` 显示本插件占位者的 `priority` 是 `-3`，
而代码里写的是 `-1`。先排除「注册重复」：`occupants` 里 `dyn/chgset-1` **只有一条**
（重复注册会出现两条），而且 `dsh-client-ui-slots/lib/index.js:120` 与 `:247`
两处都逐字保留 / 回读 `options.priority`——所以 `-3` 不是我写的那次调用。

真因在动态插件运行时 `dsh-cordis-client-runner/lib/client.js:266-271`：

```js
const spec = slots.spec(slot)
let priority = options.priority
if (spec === void 0 || spec.kind !== "chain") {
  priority = env.allocatePriority()      // ← 非 chain 槽：传入值被丢弃
  options.priority = priority
}
```

**任何非 `chain` 槽，我传的 `priority` 都会被运行时用 `env.allocatePriority()` 覆盖。**
`details` 是 `single`，所以在那里写的 `priority: -1` 是**死代码**。

该运行时的设计意图（`:383` 注释「Page-local shadowing rank. A later registration
receives a lower priority.」，以及 `:3306` 对 `root` 槽的说明）是：
**动态注册的条目一律拿到比出厂条目更低的优先级**，从而稳定遮蔽出厂 UI。
也就是说「本面板会赢」是框架保证的，不依赖我选对数字——比原先以为的更稳。

但它同时意味着**我控制不了这个秩**，见边界 15。

顺带确认：`chain` 槽不受这个覆盖影响，所以卡片在
`conversation.chat.turnTail` 上写的 `priority: -1` 是**真实生效**的，必须保留。

15. **右栏占位对「后注册的动态插件」不设防**。`details` 的运行时秩由注册次序决定
    （越晚越低），所以另一个动态插件只要**晚于本插件**注册 `details`，就会遮蔽本插件。
    出厂 UI 不受此影响（动态条目恒低于出厂条目）。本插件自身换了 4 个版本
    （pkg-4 → pkg-7）后秩从 `-1` 走到 `-3`，正说明这个秩是每次注册递增的。

### 9.9 一条环境教训：数行数不要用 `Get-Content`

统计本文件行数时，`(Get-Content).Count` 给出 **236**，而
`[System.IO.File]::ReadAllLines(...)` 与 `read` 工具都给出 **399**。
该文件是 **LF-only**（`crlf=0`、`lf=399`），此处的 `Get-Content` 对 LF-only 文件会少算。
需要行数时用 `[System.IO.File]::ReadAllLines($p, [System.Text.Encoding]::UTF8).Length`。

## 十、状态更新：pkg-8 —— 加宽与样式，以及一个必须先说的缺陷

### 10.1 右栏宽度：平台自身到不了 520 以上

`layout` 服务只暴露 `toggleSidebar / openDetails / closeDetails`；
真正写宽度的 `setDetails` 是内部 action，且被钳位：

```js

```

所以无论怎么拖，右栏上限都是 520。要更宽只能覆盖 frame 的行内
`grid-template-columns`（`ui-layout:243`），这必须 `!important`。

两点保护：

- **不写死侧边栏宽度**：从 frame 的行内样式读出侧边栏轨宽写进 `--tchg-sb`，
  用户拖过的侧边栏宽度会被保留。
- **`:has()` 的可用性有证据**：本仓出厂 CSS 就在用
  （`dsh-client-ui-primitives/lib/JsonTree.module.css:46`、
  `markdown/MarkdownText.module.css:54`）。

**已知副作用**：`!important` 会让拖动分隔条失效（拖动写的是 store，会被规则压过）。
因此做成面板里的开关，默认「加宽」，点「还原」立刻回到平台宽度且拖动恢复。

### 10.5 一个必须先说的缺陷：状态只活在内存里

**症状（用户实测）**：插件每更新一个 Package，之前所有回合的变更卡片一起消失。

**原因**：`sealed` 这个 Map 活在 Host 半部的 fiber 里。动态插件更新
= 旧 fiber 销毁 + 新 fiber 建立，模块级内存随之清空。于是：

- 更新前封存的 change set 全部丢失；
- 客户端的 `changedTurns` 索引也一起清空（它同样只在内存里）；
- `turn-changes/get` 对新 fiber 来说查不到任何回合，返回 `found: false`，
  卡片组件直接 `return null` —— 表现是「卡片不见了」，而不是报错。

这不是小毛病，而是**设计缺陷**：卡片数据从来没有落盘，
既扛不住插件更新，也扛不住进程重启。前面几轮连续发版（pkg-5 → pkg-8）
把它暴露了出来。

**已解决（v11）**：见第十一节。封存的 change set 现在写进相对路径
`turn-changes/<sessionId>.json`，启动时读回并随第一次轮询送给客户端，
所以插件更新与进程重启后卡片都会恢复。实测确认：一个回合结束后该文件真的出现在
磁盘上，且其 `add`/`del` 与卡片显示的数字一致（`turn=22 add=72 del=0`）。
追不回的只有**本版之前**的历史回合——它们从未落过盘。

## 十一、崩溃根因更正（实测）与落盘方案

### 11.1 更正：不是会话日志 OOM

崩溃后我一度把它归因于 `ctx.sessionQuery.readSession` 的全量加载与逐事件深拷贝——那个说法只出现在当时的对话里，并没有写进本文档。**而这个判断是错的。** `logs/harness.log` 里有完整证据链：

```
unhandled rejection: TypeError: Cannot read properties of undefined (reading 'trim')
    at resolveLocalTarget (dsh-fs-local/lib/index.js:154:11)
    at Proxy.resolve      (dsh-fs-local/lib/index.js:706:23)
    at Proxy.checkedTarget(dsh-fs-sandbox/lib/index.js:158:28)
    at Proxy.writeText    (dsh-fs-sandbox/lib/index.js:126:37)
    at writeReport        (cordis-dyn-chgset-1.js:38:14)
dsh: fatal load failure: TypeError: Cannot read properties of undefined (reading 'trim')
[node] Harness process exited (exit code 1)
```

两个错误叠在一起：

1. `fs.writeText(REPORT, text)` 传的是**字符串路径**，而它要的是 **target 对象**（`await ctx.fs.resolve(path)` 的返回值）。`dsh-fs-sandbox` 于是拿 `undefined` 去 `resolve`，在 `dsh-fs-local:154` 的 `path.trim()` 上炸掉。
2. 这一行**没有 await**，`try/catch` 抓不到异步 rejection，它变成 unhandled rejection，直接把宿主进程打死。

教训：`ctx.fs` 的每个方法都必须 `await` 并 `catch`——漏掉 await 的代价是整进程退出。附带结论：`sessionQuery` 并不是崩溃原因，但第九节关于它代价极高的判断仍成立；落盘方案不需要它，所以保持禁用。

### 11.2 实测得到的 fs 沙箱契约

用 `[turn-diag]` 在 `logs/harness.log` 里打点实测（不是读代码猜的）：

| 目标 | resolve | writeText |
| --- | --- | --- |
| `D:/AI/DeepseekPlugin/.scratch/...`（工作区绝对路径） | OK | `FS_SANDBOX_DENIED` |
| `C:/Users/.../harness/...`（DSH_HOME 绝对路径） | OK | `FS_SANDBOX_DENIED` |
| `turn-changes/state-probe.json`（**相对路径**） | OK | OK（`operation: create`） |

原因：插件的 `fs` **不携带会话的 workspace 授权**，沙箱只允许写它自己的根（进程 cwd，即 `userData/launch-root`）。相对路径会自动落在那个根下，子目录会被自动创建，`listDir` 也能正常列举。

**所以状态一律用相对路径，不硬编码任何机器路径。**

### 11.3 观测通道

宿主 `console.log` 会写进 `logs/harness.log`，带 `[cordis:<pluginId>]` 前缀。这给了一个**不需要用户转述**的诊断通道，11.1 与 11.2 的结论全部由此得到。落盘层现在把每条诊断同时写进 console 与 `turn-changes/_status.json`。

### 11.4 落盘方案（v11）与自检

- 目录：相对路径 `turn-changes/`；每会话一个 `<sessionId>.json`，另有 `_status.json` 记录 revision、会话清单与诊断 notes。
- 写入时机：每次 `seal` 之后。上限 30 个回合 / 6,000,000 字符，超限从最旧回合开始丢。
- 启动时 `restoreAll()` 读回全部变更集，并把 `revision` 提到历史最大值；随后第一次轮询（`since: 0`）就会把它们送给客户端，**卡片因此恢复**。
- 全部 fs 调用 `await` + `catch`，任何失败只降级为「不落盘」，绝不抛出。

实测自检（`turn-changes/_status.json`，v12 启动后的真实内容）：

```json
{
  "revision": 2,
  "sessions": ["session-96af4672-39e3-43a5-b4c1-8e4fb582dee3=2"],
  "notes": [
    "stateDir | ready .../launch-root/turn-changes/.probe",
    "restored | 2 change sets across 1 sessions"
  ]
}
```

这一次的读回不是「首次启动、目录为空」，而是**插件从 v11 更新到 v12、内存里的 `sealed` 被整个销毁之后**发生的：两个变更集确实是从磁盘读回来的，卡片也真的恢复了。`logs/harness.log` 里能看到完整先后顺序：

```
restored | 0 change sets across 0 sessions   ← v11 启动
saved    | session-... sets=1 chars=6931      ← 回合 22 封存
saved    | session-... sets=2 chars=9466      ← 回合 23 封存
restored | 2 change sets across 1 sessions    ← v12 启动，两张卡片回来
```

`.probe` 是一次写入 + 读回的往返校验，通过即说明这条链路真的可用。

### 11.5 仍然诚实的边界

1. **历史回合追不回来**：数据从来没有落过盘，v11 是第一个会落盘的版本。卡片从 v11 运行期间发生的回合开始出现。
2. **`撤销` 仍未接通**，按钮保持 `disabled`——不假装能用。
3. `launch-root` 属于桌面端实现细节；若将来 DSH 改掉这个 cwd，落盘会降级为不落盘（不会崩，但卡片又会丢）。

## 十二、v12–v13：把审查面板补到与 Cindy 同形

### 12.1 v12：diff 背景色照搬 Cindy

平台自己的 diff 只设文字颜色、不设行背景（`dsh-client-ui-primitives/lib/DiffBlock.module.css:61-77` 里 `.del`/`.add` 只有 `color`）；Cindy 是整行上色。所以直接照搬 Cindy 的设计 token 数值（出处 `refs/cindy/packages/design-tokens/src/reference/color.json:6974-7279`）：

| token | light | dark |
|---|---|---|
| `diff-add-bg` / `diff-add-fg` | `#F0FFF4` / `#22863A` | `#033A16` / `#7EE787` |
| `diff-del-bg` / `diff-del-fg` | `#FFEEF0` / `#B31D28` | `#67060C` / `#FF7B72` |
| `diff-add-emphasis` | `#ACF2BD` | `rgba(46,160,67,.42)` |
| `diff-del-emphasis` | `#FFD7D5` | `rgba(248,81,73,.42)` |

用法照搬 `PlainUnifiedDiff.tsx:49-53`：bg 与 fg **成对挂在整行**，**上下文行不上色**。明暗切换用出厂机制 `body[data-ds-dark-theme]`（`dsh-client-ui-theme/lib/index.js:46` 的 `toggleAttribute`），纯 CSS，不需要 JS 探测。同时删掉了行悬停底色——它会盖掉红/绿，而 Cindy 的 diff 行本来就没有悬停态。

### 12.2 v13：分栏按 Cindy 配对

原先分栏是把删除行和新增行各占一行，Cindy 不是这样。照搬 `diffRows.ts:284-297` 的 `pairChangedLines`：把一段连续的改动行收成 `deletes[]`/`adds[]`，然后**按下标配对** `pair[i] = {deletes[i] ?? null, adds[i] ?? null}`，行数取 `max`。于是 3 删 1 增渲染成 4 行，新增配在第 1 行——`diffRows.ts:76-78` 的注释专门讲了这一点。上下文行左右两半是同一行。

半栏结构照搬 `PlainUnifiedDiff.tsx:192-238`：`grid-cols-2`，每半栏是 `[行号][符号][内容]`，整半栏上色，**空缺的那半栏用 surface 色**。

实测（`.scratch/verify-pairing.mjs` 跑磁盘上真实 rows，不是合成样例）：

| 回合 | 主机 rows | 改动行 | 分栏渲染行 | 同行成对 |
|---|---|---|---|---|
| 22 | 78 | +72 / −0 | 77 | 0 |
| 23 | 28 | +6 / −7 | 19 | 6 |

不变量全部成立：统一视图不丢行；每个删除行恰好出现在左半栏一次；每个新增行恰好出现在右半栏一次；上下文行左右同一；词级区间升序、不重叠、不越界。

### 12.3 v13：词级高亮

照搬 `inlineDiff.ts`：只对**两侧都存在的**配对行做（`:127`）；四项门槛与 Cindy 一致（单行 > 1000 字符不做、公共比例 < 0.3 不做、任一侧为空不做、总配对数 > 150 或总字符 > 200,000 整文件跳过，`:53-96` 与 `:141-153`）；区间按 `mergeInlineDiffRanges`（`:98-120`）合并——截断 → 丢空区间 → 排序 → `start <= previous.end` 就合并；渲染成 `border-radius:2px` + emphasis 底色的 `span`（`:32-35`）。

分词器按 `diff@9.0.0` 的 `diffWordsWithSpace`（`node_modules/diff/libesm/diff/word.js:274`）实现。**这里有一处不等价**：jsdiff 用 Myers 中间蛇算法 + `timeout: 20`，我用 LCS DP + token 数上限；最小编辑脚本在歧义处可能不同，因而高亮**边界可能相差一个 token**。对视觉没有影响，但不是逐字节等同。

真实数据上值得说明的现象：回合 23 的 13 个改动行里**只有 2 行**拿到高亮，因为其余 11 行是整行重写，公共比例低于 0.3，被 Cindy 自己的门槛拒掉了。拿到高亮的那两行，恰好是之前某一轮我自己改这份文档时的行：

```

新 526  崩溃[后我一度把它]归因于 ……深拷贝[——那个说法只出现在当时的对话里，并没有写进本文档]。
```

## 十三、v14–v18：把工具详情接回右栏，并改成自动打开

### 13.1 那块区域叫什么，以及我当初造成的回归

| 名字 | 位置 |
|---|---|
| `details` | 客户端座位名，`kind: single`、`scope: session` |
| `detailsCol` | 布局里的第三列（网格轨道） |
| `panels.details` | 布局状态里这一列的宽度，0 即收起 |
| `openDetails` / `closeDetails` / `setDetails` | `ctx.layout` 上的三个动作 |
| `[data-details-collapsed]` | 收起时挂在网格容器上的属性 |
| `conversation.details.tool` | 出厂 DetailsPanel 在这个位置声明的子座位 |

出厂占位者（`dsh-client-ui-chat` 的 `DetailsPanel`）读的是 `useStore(s => s.selection)`——每会话共享的 Chat 选择 store——所以「点一个工具调用 → 右栏出详情」本来是出厂行为。我占用 `details` 后（`single` 只渲染胜者，我的条目 rank 更低所以胜出，出厂条目变成 `active:false`），这一路就断了。这正是本节要修的东西。

### 13.2 实测出的座位规则

四条，全部来自 `harness.log` 里的实测报错与取值，不是从类型声明推的：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 座位声明是**全局**的，一个 key 只能被一个条目声明 | 我声明 `conversation.details.tool` 报 `slot "conversation.details.tool" is already declared (by an entry in "details" (H5))` |
| 2 | `renderSlot` 只认**本条目自己声明的** children，不是通用渲染器 | 拿别家已声明的座位调用报 `slot 'conversation.details.tool' is not declared by this entry's children` |
| 3 | 声明一个**自己的**、没人占的子座位可以成功，并因此换来 `renderSlot` / `useStore` / `actions` / `SessionProvider` | `diag.props:children+store` 里出现了这四个 prop |
| 4 | `slots.entriesOfSlot(key)`（未文档化）能读到同座位的条目；`slots.isLive` 不存在 | `diag.slots.shape`、`diag.liftedStore`、`diag.toolEntry` |

1 与 2 联手封死了「声明子座位再用 `renderSlot` 渲染出厂工具详情」这条路，只剩「把座位占用者**自己渲染出来**」这一条。

顺带两条可复用的内部约定：

- **store 句柄可以借。** 出厂 `details` 条目上的 `store`（`create` 是函数、`spec` 是 `init,actions`）就是那个每会话共享的 Chat store 句柄。我把它当作自己条目的 `store`，于是拿到同一实例的 `useStore`——出厂的选择态因此能在我的面板里原样读出来。
- **注入的 `hooks.{name}` 会变成组件的 `use{Name}` prop。** `dsh-client-ui-tool/lib/client.js:2105` 的 `toolInject = () => ({ hooks: { hostInfo } })` 正对上 `:1442` 的 `function ToolDetails({ block, cwd, useHostInfo, t })`。`hostInfo` 是 `{ getSnapshot, subscribe }` 形状（外部 store），所以能自己用 `React.useSyncExternalStore` 包一个 `useHostInfo` 出来。

### 13.3 v17 / v18 的做法

注册按三条依次尝试，实测落在第一条：

```
children: { 'conversation.details.review': { kind:'single', scope:'session' } } + store: <借来的句柄>
  → 仅 store
  → 仅 name
```

这是代价最小的一次举手：声明一个没人用的子座位，换来上面那四个 prop；三层 fallback 保证任一条被拒都不会把面板打空。

右栏变成两个页签：

- **审查**：v13 的 diff 面板，本次未改动。
- **工具详情**：头部（工具名）+ 输入段（`argsRaw` 美化）+ 输出段。输出段先用 `renderSlot`，实测它必然抛错，于是走手工渲染——把座位占用者组件用 `React.createElement` 装起来，props = 我的全套标准 props + `block`/`cwd` + `locale.bind('conversation')` 得到的 `t` + 由 `hooks.hostInfo` 包装出的 `useHostInfo`，外面套出厂 `SessionProvider`，最外层再套一个 React **错误边界**（类组件 + `getDerivedStateFromError`）。任一步失败都退回出厂同款的原始文本 `pre`（`data-error` 也照搬）。

**自检**是本轮唯一「不用等人点」就能拿到证据的办法：面板挂载时用会话里**真实的**已封存工具块，在 `display:none` 容器里把上面这套渲染一次，只做一次，结果写进日志：

```
diag.boundary.selftest | mounted-ok
```

**自动打开**：新回合封存后，客户端长轮询收到新条目 → 选中该回合 → `ctx.layout.openDetails()`。两处限定：首次轮询（从落盘恢复的历史变更集）不触发，避免每次启动都弹；只在右栏当前所在会话的回合上触发，避免被后台会话抢走。

### 13.4 仍然诚实的边界

1. **手工渲染是绕过座位系统的做法**，借用了未文档化的 `entriesOfSlot`。它今天成立，DSH 升级后可能失效；失效时的表现是退回原始文本（可见、不崩），不是白屏。
2. **自检只证明「不抛错」**，不证明每张卡片的分支都对。`ToolDetails` 依次尝试终端/读取/diff/搜索/web 模型，自检跑到的是那块真实数据命中的那一支，其余分支没验。
3. 自动打开的**端到端**效果在对话里无法自证：`openDetails()` 与出厂布局的会话门控只在下一回合结束时才会走到，届时看日志里的 `diag.autoOpen`。
4. `renderSlot` 每次渲染仍会试一次（仅在选中了工具调用时），失败后置位不再重试。这是有意保留的一次性探测，不是遗留代码。
5. 本节对应 `chgset-1/pkg-11`（v18），上一版 pkg-6 是 v13。

两条必须记住的结论：

1. **注册函数是清单，不是可以顺手重写的小工具。** 重写 `mount()` 时必须先把原有注册逐条列出来对照。这一轮我把面板注册重写了五次，每次都验了面板与工具详情，却没有回头看卡片——所以这个回归活了五个版本才被你发现。验证必须**同时**覆盖卡片与面板两条路径。
2. **预测更正。** 我在上一轮预测卡片会显示 `+775 −0 / 4 个文件`，实际是 `+119 −0 / 3 个文件`。差的是 `.scratch/before-14.md`：它由 node 脚本用 `writeFileSync` 写出，而插件的捕获只认 `edit`/`write` 工具调用，脚本直接写盘的文件不进卡片。这不是插件缺陷，是我预测时把「文件被创建了」当成了「文件被工具写了」。
